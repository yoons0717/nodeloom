# 성능 기록

에디터 캔버스의 렌더링 성능을 같은 기기, 같은 동작으로 재서 개선 전후를 비교한다.

M2·M6에 잰 기준선 표는 M9의 "개선 전"과 같은 수준이라 지웠다(저장소 기록 `git log -p docs/PERFORMANCE.md`에 남아 있다).

## 재는 방법

```bash
pnpm --filter @nodeloom/browser-tests exec playwright install chromium   # 처음 한 번
pnpm --filter @nodeloom/browser-tests bench
```

- `NEXT_PUBLIC_BENCH=1`로 web을 **프로덕션 빌드**한 뒤 띄워서 잰다. 개발 모드는 React가 검사용으로 렌더를 두 번 하는 등 수치가 부푼다. `/bench` 페이지와 React Profiler 측정은 이 빌드와 개발 모드에서만 켜진다.
- `/bench?nodes=N`은 Trigger 하나와 Transform N-1개를 격자로 놓고 앞 노드와 이은 그래프를 연다. 설정이 모두 올바라서 오류 배지는 없다.
- 동작마다 준비 운동 1번은 버리고, 3번 잰 값의 중앙값을 적는다.
  - **드래그:** 화면에 보이는 노드 하나를 잡고 300px 끌고 갔다가 제자리로 돌아와 놓는다(마우스 이동 60번).
  - **선택 변경 10회:** 화면에 보이는 노드 10개를 차례로 누른다.
- 측정 항목
  - **노드 리렌더:** 노드 카드 컴포넌트가 다시 그려진 횟수(노드 카드마다 둔 React Profiler)
  - **커밋 수, 렌더 시간 합:** 에디터 전체를 감싼 React Profiler의 커밋 횟수와 `actualDuration` 합. 성능 HUD가 1초마다 숫자를 갱신하는 커밋(측정 구간마다 1~3번, 노드 리렌더 없음)도 들어 있다
  - **프레임:** `requestAnimationFrame` 사이 간격. 60Hz 화면에서 16.7ms면 끊김이 없고, 33ms나 50ms는 프레임을 1~2개 놓쳤다는 뜻이다.
- CI에서는 돌리지 않는다. 실행 환경마다 수치가 달라서 같은 기기 안에서만 비교한다.

## M9 9-a: 바뀐 노드만 다시 그리기 (2026-10-16)

환경: Apple M1, 메모리 16GB, macOS 27.0.1, Playwright 1.63.0의 Chromium(헤드리스), 창 1400×900. 같은 날 개선 전·후를 2번씩 돌렸고, 표는 각각 첫 번째 실행이다.

| 노드 수 | 동작 | 노드 리렌더 | 렌더 시간 합(ms) | 프레임 p95(ms) | 가장 긴 프레임(ms) |
|---|---|---|---|---|---|
| 20 | 드래그 | 1082 → 56 | 91.6 → 64.0 | 16.8 → 16.8 | 16.8 → 16.8 |
| 20 | 선택 변경 10회 | 200 → 20 | 9.4 → 7.2 | 16.7 → 16.7 | 16.8 → 16.8 |
| 200 | 드래그 | 12002 → 62 | 306.8 → 57.0 | 16.7 → 16.8 | 16.8 → 16.8 |
| 200 | 선택 변경 10회 | 2000 → 20 | 31.4 → 8.7 | 16.7 → 16.8 | 16.8 → 16.8 |
| 1000 | 드래그 | 60002 → 62 | 1562.5 → 72.8 | 66.6 → 16.8 | 66.8 → 16.8 |
| 1000 | 선택 변경 10회 | 10000 → 20 | 105.1 → 10.4 | 33.4 → 16.7 | 50.1 → 16.8 |

개선 전에는 노드 하나를 움직이거나 선택만 바꿔도 모든 노드 카드가 다시 그려졌다(선택 변경 10회 = 노드 수 × 10). 커밋 수와 프레임 중앙값(16.7ms)은 전후가 같다.

### 무엇을 바꿨나

- **노드·연결선 객체를 그대로 넘기기**(`canvas.tsx`): React Flow는 이전과 같은 객체를 받은 노드는 다시 그리지 않는다. 그래프의 노드 객체마다 마지막으로 만든 React Flow 객체를 `WeakMap`에 기억해 두고, 선택 여부·오류 목록·크기가 같으면 그대로 넘긴다. 오류 목록은 검사할 때마다 새 배열이라 내용(code·field·message)으로 비교한다.
- **위치만 바뀌면 검사 결과 다시 쓰기**(`graph-issues.ts`): 노드 1000개 그래프의 `validateGraph` 한 번이 Node에서 16.5ms(한 프레임)였다. 검사 결과는 위치와 상관없으므로, 직전 그래프와 비교해 위치만 바뀌었으면 직전 결과를 그대로 쓴다.

### 읽는 법

- 선택 변경은 선택이 풀린 노드와 새로 선택된 노드 2개만, 드래그는 끄는 노드 하나만 다시 그린다. 그래서 리렌더 수가 노드 수와 상관없다.
- 1000개 드래그의 렌더 시간 합이 약 95% 줄고 프레임을 놓치지 않는다. 두 번째 실행은 83.1ms, 가장 긴 프레임 33.3ms가 한 번 나왔다.
- 객체를 그대로 넘기는 것만 넣었을 때는 1000개 드래그가 866.6ms, p95 33.4ms였다. 남은 시간의 대부분이 드래그마다 다시 하던 검사였다.
- 노드 카드를 `memo`로 감싸는 것은 필요 없었다.
- 같은 조건에서 실행마다 렌더 시간 합이 5~10%, 1000개의 가장 긴 프레임이 50~67ms까지 흔들린다.

## M9 9-b: 화면별 JS 크기와 LCP·INP (2026-10-16)

### 재는 방법

```bash
pnpm --filter @nodeloom/browser-tests vitals
```

- e2e와 같은 서버(새 Postgres, api·web 프로덕션 빌드)를 띄우고, 예시 워크플로우를 만들어 한 번 실행한 뒤 잰다.
- 화면마다 캐시 없는 새 브라우저로 3번 열어 중앙값을 적는다.
  - **JS:** 그 화면을 열 때 받은 `.js` 파일의 전송 크기 합(압축된 크기)
  - **LCP**(Largest Contentful Paint): 화면에서 가장 큰 내용이 그려지기까지 걸린 시간
  - **INP**(Interaction to Next Paint): 클릭·키 입력 뒤 화면이 바뀌어 보이기까지 걸린 시간. 에디터는 노드를 고르고 URL 칸에 4글자를 입력하고, 실행 상세는 노드를 골라 출력을 연다
- LCP·INP는 `web-vitals`(Chrome 팀의 측정 라이브러리)로 잰다. 앱에는 넣지 않고 Playwright가 페이지를 열 때 주입한다.
- 로컬이라 네트워크 지연이 없어서 LCP·INP는 작게 나온다. 실제 네트워크에서는 JS 크기가 받는 시간으로 그대로 이어지므로 JS 크기를 주로 본다.

### 결과

| 화면 | JS 개선 전(KB) | JS 개선 후(KB) | LCP(ms) | INP(ms) |
|---|---|---|---|---|
| 목록 | 379.5 | 324.9 (-54.6) | 64 | - |
| 에디터 | 486.9 | 486.6 | 212 | 72 |
| 실행 상세 | 442.9 | 386.8 (-56.1) | 80 | 64 |

LCP·INP는 개선 전후 모두 위와 비슷했다(실행마다 ±20ms 안).

### 무엇을 바꿨나

Next.js는 화면(라우트)마다 그 화면이 import로 이어지는 코드만 묶어 내려보낸다. 그런데 목록과 실행 상세는 쓰지 않는 JSONata(식 계산)와 cron-parser·luxon(cron 해석)을 받고 있었다. 셋 다 에디터에서만 쓴다.

| 원인 | 고친 것 |
|---|---|
| core의 `index.ts`가 모든 파일을 다시 내보내는데(`export *`) "부작용 없음" 표시가 없어서, 번들러가 안 쓰는 파일(식 계산)을 빼지 못했다 | core `package.json`에 `"sideEffects": false` |
| 그래프 형식 검사(`graphSchema`)의 노드 종류 목록이 `NODE_SPECS`에서 만들어져, 설정 규칙(Trigger의 cron 검사)까지 끌려왔다 | 노드 종류 목록(`NODE_TYPES`)과 포트(`NODE_PORTS`)는 `graph.ts`에 두고, 설정 규칙(`NODE_SPECS`)은 `node-specs.ts`로 옮겼다. 노드 카드는 포트만 쓴다 |
| 실행 상세가 쓰는 캔버스 도구 막대와 같은 파일에 에디터의 되돌리기 버튼이 있어서, 에디터 스토어와 식 문법 검사까지 끌려왔다 | 되돌리기 버튼을 `undo-redo.tsx`로 옮겼다 |

이름과 동작은 바뀌지 않았다(core의 내보내기 이름 그대로, 테스트 그대로 통과).

### 남은 것

- **zod 언어 파일(압축 약 40KB):** 모든 화면이 zod를 쓰는데, zod가 지원하는 모든 언어의 오류 문구가 함께 들어온다. 이 프로젝트는 오류 문구를 직접 쓰므로 쓰지 않는다. `import { z } from 'zod'`로 `z` 묶음 전체를 가져오는 방식이라 번들러가 골라내지 못한다. 혼자 쓰는 도구라 체감 차이가 크지 않고, 줄이려면 검사 구조를 바꿔야 해서 M9에서는 그대로 둔다(BACKLOG).
- **에디터:** JSONata·cron-parser·luxon·React Flow를 실제로 쓰므로 그대로다.

## M9 9-c: 큰 JSON 보기 (2026-10-16)

`pnpm --filter @nodeloom/browser-tests vitals`의 "큰 JSON 보기"로 잰다. 연습용 응답 `/mock/items/15000`(항목 1만 5천 개, 약 0.94MB)을 받은 HTTP 노드를 실행 상세에서 눌러, JSON 보기가 다 그려지기까지를 3번 잰 중앙값이다.

| 항목 | 값 |
|---|---|
| 누른 순간부터 화면의 요소 수가 더 늘지 않을 때까지(출력을 받아 오는 시간 포함) | 142ms |
| 새로 생긴 요소 수 | 45,021 |
| 가장 긴 작업(그동안 클릭·스크롤이 먹지 않음) | 221ms |

- JSON 보기는 처음에 두 단계까지 펼치므로, 위쪽에 있는 큰 배열은 항목마다 한 줄씩 모두 그린다.
- 221ms는 조작 뒤 반응 기준(200ms 이하가 "좋음")을 조금 넘는다. 느린 기기에서는 몇 배 길어질 수 있다.
- **고치지 않았다.** 이 정도 크기의 응답은 드물고(평소 흐름은 수십 줄), 이 기기에서는 눈에 띄는 멈춤이 아니다. 고친다면 큰 배열·객체는 처음 일부만 그리고 "더 보기"로 이어 그리는 방법이 가장 작다(BACKLOG).
