# 성능 기록

에디터 캔버스의 렌더링 성능을 같은 기기, 같은 동작으로 재서 개선 전후를 비교한다.

## 재는 방법

```bash
pnpm --filter @nodeloom/browser-tests exec playwright install chromium   # 처음 한 번
pnpm --filter @nodeloom/browser-tests bench
```

- `NEXT_PUBLIC_BENCH=1`로 web을 **프로덕션 빌드**한 뒤 띄워서 잰다. 개발 모드는 React가 검사용으로 렌더를 두 번 하는 등 수치가 부푼다. 이 빌드에서만 `/bench` 페이지와 React Profiler 측정이 켜진다.
- `/bench?nodes=N`은 Trigger 하나와 Transform N-1개를 격자로 놓고 앞 노드와 이은 그래프를 연다. 설정이 모두 올바라서 오류 배지는 없다.
- 동작마다 준비 운동 1번은 버리고, 3번 잰 값의 중앙값을 적는다.
  - **드래그:** 화면에 보이는 노드 하나를 잡고 300px 끌고 갔다가 제자리로 돌아와 놓는다(마우스 이동 60번).
  - **선택 변경 10회:** 화면에 보이는 노드 10개를 차례로 누른다.
- 측정 항목
  - **노드 리렌더:** 노드 카드 컴포넌트가 다시 그려진 횟수(노드 카드마다 둔 React Profiler)
  - **커밋 수, 렌더 시간 합:** 에디터 전체를 감싼 React Profiler의 커밋 횟수와 `actualDuration` 합. 성능 HUD가 1초마다 숫자를 갱신하는 커밋(측정 구간마다 1~3번, 노드 리렌더 없음)도 들어 있다
  - **프레임:** `requestAnimationFrame` 사이 간격. 60Hz 화면에서 16.7ms면 끊김이 없고, 33ms나 50ms는 프레임을 1~2개 놓쳤다는 뜻이다.
- CI에서는 돌리지 않는다. 실행 환경마다 수치가 달라서 같은 기기 안에서만 비교한다.

## 기준선: 최적화 전 (M2, 2026-10-06)

환경: Apple M1, 메모리 16GB, macOS 27.0.1, Playwright 1.63.0의 Chromium(헤드리스), 창 1400×900

|---|---|---|---|---|---|---|---|
| 20 | 드래그 | 1122 | 113 | 60.6 | 16.7 | 16.7 | 16.8 |
| 20 | 선택 변경 10회 | 200 | 21 | 6.6 | 16.7 | 16.8 | 16.8 |
| 200 | 드래그 | 12002 | 121 | 273.6 | 16.7 | 16.7 | 16.8 |

| 1000 | 선택 변경 10회 | 10000 | 22 | 99.7 | 16.7 | 33.3 | 33.4 |

실행할 때마다 렌더 시간 합은 5% 안에서 달라졌다. 드래그의 노드 리렌더는 마우스 이동이 위치 변경 몇 번으로 묶이느냐에 따라 노드 수만큼(한 바퀴) 차이가 날 수 있다.

### 읽는 법

- **노드 하나를 움직이거나 선택만 바꿔도 모든 노드 카드가 다시 그려진다.** 선택 변경 10회의 리렌더가 정확히 노드 수 × 10이고, 드래그도 위치가 바뀔 때마다 노드 수만큼 다시 그려진다. 에디터가 그래프 전체를 구독하고 매번 React Flow에 새 노드 배열을 넘기기 때문이다.
- 노드 20개, 200개에서는 그래도 프레임이 밀리지 않는다. 1000개에서는 드래그 중 프레임 일부가 50~67ms까지 늘어나(프레임을 2~3개 놓침) 끊김이 보인다.
- 개선은 M9에서 한다. 바뀐 노드만 다시 그리도록 고친 뒤 같은 벤치로 다시 재서 아래 "M6 노드 카드 기준선"과 비교한다.

## 기준선: M6 노드 카드 (2026-10-11)

M6 디자인 정리에서 노드 카드를 바꿨다(136×84 고정, 종류 글리프, 설정 요약 줄, 포트 12px). 위 M2 기준선은 이전 카드로 잰 값이라 **M9 성능 개선은 이 표와 비교한다**. 최적화는 아직 하지 않았다.

- 모든 카드가 다시 그려지는 구조는 그대로라 리렌더 수는 M2와 같다(드래그 20개는 위치 변경이 묶이는 횟수에 따라 한 바퀴 차이).
- 렌더 시간 합은 200개·1000개에서 M2보다 3~6% 늘었고, 20개 드래그는 줄었다(60.6 → 48.3ms). 벤치를 한 번 돌린 값(동작마다 3번 잰 중앙값)이라 실행마다 생기는 차이(M2 때 5% 안)와 구별하기 어렵다.
- 1000개 선택 변경의 가장 긴 프레임이 50ms로 M2(33ms)보다 길었다. M9 개선 전에 벤치를 한 번 더 돌려 확인한다.

### 무엇을 바꿨나

- **노드·연결선 객체를 그대로 넘기기**(`canvas.tsx`): React Flow는 이전과 같은 객체를 받은 노드는 다시 그리지 않는다. 그래프의 노드 객체마다 마지막으로 만든 React Flow 객체를 `WeakMap`에 기억해 두고, 선택 여부·오류 목록·크기가 같으면 그대로 넘긴다. 오류 목록은 검사할 때마다 새 배열이라 내용(code·field·message)으로 비교한다.
- **위치만 바뀌면 검사 결과 다시 쓰기**(`graph-issues.ts`): 노드 1000개 그래프의 `validateGraph` 한 번이 Node에서 16.5ms(한 프레임)였다. 검사 결과는 위치와 상관없으므로, 직전 그래프와 비교해 위치만 바뀌었으면 직전 결과를 그대로 쓴다.

### 읽는 법

- **선택 변경 10회의 노드 리렌더가 노드 수와 상관없이 20이다.** 한 번 바꿀 때 선택이 풀린 노드와 새로 선택된 노드 2개만 다시 그린다.
- **드래그의 노드 리렌더도 노드 수와 상관없이 56~62다.** 끄는 노드 하나가 위치가 바뀔 때마다 한 번씩 다시 그려진 수다.
- 1000개 드래그의 렌더 시간 합이 1562 → 73ms(약 95% 감소), 프레임 p95가 66.6 → 16.8ms로 프레임을 놓치지 않는다. 두 번째 실행은 83.1ms, 가장 긴 프레임 33.3ms가 한 번 나왔다.
- 첫 번째 변경만 넣었을 때(검사 다시 쓰기 전)는 1000개 드래그가 렌더 시간 합 866.6ms, p95 33.4ms였다. 남은 시간의 대부분이 드래그마다 다시 하던 검사였다.
- 노드 카드를 `memo`로 감싸는 것은 하지 않았다. 객체를 그대로 넘기는 것만으로 리렌더가 바뀐 노드 수만큼으로 줄었다.
- 개선 전 두 실행의 차이: 렌더 시간 합 5~10%, 1000개의 가장 긴 프레임 50~67ms. 그래서 M6 기준선에서 본 "가장 긴 프레임 33 → 50ms 늘어남"은 측정 흔들림으로 본다.
