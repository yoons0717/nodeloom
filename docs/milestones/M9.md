# M9 성능 개선

> **상태: 완료 (2026-10-16).** 상위 문서: `docs/PROJECT_PLAN.md` 4절.

## 왜 하나

`docs/PERFORMANCE.md`의 M6 기준선을 보면, 노드 하나를 끌거나 선택만 바꿔도 모든 노드 카드가 다시 그려진다. 선택 변경 10회의 리렌더가 정확히 "노드 수 × 10"이다. 노드 1000개를 끌면 프레임이 67ms까지 늘어 2~3장을 놓친다.

원인은 `canvas.tsx`가 그래프가 바뀔 때마다 모든 노드의 React Flow 객체(`data`, 오류 목록 포함)를 새로 만들기 때문이다. React Flow는 넘겨받은 노드 객체가 이전과 같으면 그 노드를 그대로 두고, 다르면 다시 그린다. 그래프 쪽은 이미 바뀐 노드만 새 객체로 만든다(`dragTo` 등).

## 목표

- **에디터:** 노드 하나를 끌거나 고를 때 그 노드만 다시 그린다. 노드 1000개에서도 드래그가 눈에 띄게 끊기지 않게 한다.
- **실행 상세:** 1MB에 가까운 출력도 JSON 보기가 멈추지 않고 열린다.
- **화면 로딩:** 목록·에디터·실행 상세가 뜨는 시간(LCP)과 누른 뒤 반응하는 시간(INP)을 재고, 에디터 전용 코드가 다른 화면을 무겁게 하지 않게 한다.
- **기록:** 개선 전후 숫자를 같은 벤치로 재서 `PERFORMANCE.md`와 README에 남긴다. 숫자 목표는 미리 정하지 않고, 잰 결과로 판단한다.

## 하지 않는 것

- 기능과 화면 바꾸기. 같은 화면을 더 적게 그리는 것만 다룬다.
- 측정 없이 고치기. 고치기 전과 후를 같은 벤치로 잰다.
- 마지막 실행 데이터 미리보기(M5 5-f). 성능 작업이 아니라 기능이라 따로 한다.

## 정한 것 (2026-10-16)

- M5의 5-e(큰 JSON 보기)를 M9에 넣는다(9-c).
- LCP·INP는 `web-vitals` 라이브러리로 잰다. Chrome과 같은 계산 방식이라 숫자를 믿을 수 있다. 앱에는 넣지 않고 Playwright가 페이지를 열 때 주입한다(앱 번들을 건드리지 않음).
- 숫자 목표는 미리 정하지 않는다. 완료 기준은 "바뀐 노드만 다시 그린다", "M6 기준선보다 줄었다"로 둔다.

## 결과 (2026-10-16)

자세한 표는 `docs/PERFORMANCE.md`의 "M9 9-a", "9-b", "9-c".

| 단계 | 결과 |
|---|---|
| 9-a 에디터 리렌더 | 노드 1000개 드래그 프레임 p95 66.6 → 16.8ms, 렌더 시간 합 1,562 → 73ms. 선택 변경 10회에 다시 그린 노드 10,000 → 20. 드래그 중 검사 다시 쓰기도 넣었다(노드 1000개 검사 한 번이 16.5ms였다). 노드 카드 `memo`는 필요 없었다 |
| 9-b 번들 | 목록 380 → 325KB, 실행 상세 443 → 387KB, 에디터 487KB 그대로. LCP·INP는 로컬에서 모두 수십~200ms대. zod 언어 파일(약 40KB)은 그대로 두었다(BACKLOG) |
| 9-c 큰 JSON | 0.94MB 출력에서 요소 4만 5천 개, 가장 긴 작업 221ms. 드문 경우라 고치지 않았다(BACKLOG) |

계획과 달라진 점:
- 9-b에서 원래 생각한 "cron 검사를 그래프 형식 검사에서 떼기"는 필요 없었다. 형식 검사는 처음부터 설정을 보지 않았고, 노드 종류 목록이 설정 규칙을 끌어오던 것이 원인이었다.
