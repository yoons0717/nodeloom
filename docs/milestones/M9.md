# M9 성능 개선

> **상태: 완료 (2026-10-16).** 상위 문서: `docs/PROJECT_PLAN.md` 4절.

## 왜 하나

`docs/PERFORMANCE.md`의 M6 기준선을 보면, 노드 하나를 끌거나 선택만 바꿔도 모든 노드 카드가 다시 그려진다. 선택 변경 10회의 리렌더가 정확히 "노드 수 × 10"이다. 노드 1000개를 끌면 프레임이 67ms까지 늘어 2~3장을 놓친다.

원인은 `canvas.tsx`가 그래프가 바뀔 때마다 모든 노드의 React Flow 객체(`data`, 오류 목록 포함)를 새로 만들기 때문이다. React Flow는 넘겨받은 노드 객체가 이전과 같으면 그 노드를 그대로 두고, 다르면 다시 그린다. 그래프 쪽은 이미 바뀐 노드만 새 객체로 만든다(`dragTo` 등).

## 목표

- **에디터:** 노드 하나를 끌거나 고를 때 그 노드만 다시 그린다. 노드 1000개에서도 드래그가 눈에 띄게 끊기지 않게 한다.
- **실행 상세:** 1MB에 가까운 출력도 JSON 보기가 멈추지 않고 열린다.
- **화면 로딩:** 목록·에디터·실행 상세가 뜨는 시간(LCP)과 누른 뒤 반응하는 시간(INP, 아래 9-b)을 재고, 에디터 전용 코드가 다른 화면을 무겁게 하지 않게 한다.
- **기록:** 개선 전후 숫자를 같은 벤치로 재서 `PERFORMANCE.md`와 README에 남긴다. 숫자 목표는 미리 정하지 않고, 잰 결과로 판단한다.

## 하지 않는 것

- 기능과 화면 바꾸기. 같은 화면을 더 적게 그리는 것만 다룬다.
- 측정 없이 고치기. 고치기 전과 후를 같은 벤치로 잰다.
- 마지막 실행 데이터 미리보기(M5 5-f). 성능 작업이 아니라 기능이라 따로 한다.

## 단계

단계마다 잰 숫자는 그 단계 끝에 `docs/PERFORMANCE.md`에 적는다(개선 전후 표, 효과가 없던 방법 포함).

### 9-a. 에디터 리렌더 줄이기
- **먼저 재기:** 지금 코드로 벤치(`pnpm --filter @nodeloom/browser-tests bench`)를 두 번 돌려 실행마다 생기는 차이를 확인한다. M6 기준선에서 1000개 선택 변경의 가장 긴 프레임이 M2보다 길었던 것(33 → 50ms)도 다시 본다.
- **바뀐 노드만 다시 그리기:** 노드마다 React Flow 객체를 만들 때, 그 노드의 그래프 값·선택 여부·오류 목록·크기가 그대로면 이전 객체를 그대로 넘긴다. 오류 목록은 내용이 같으면 같은 배열을 쓰고(오류 없는 노드는 빈 배열 하나를 함께 씀), 연결선도 같은 방식으로 한다. 그래도 다시 그려지는 노드가 측정에 남으면 그때 노드 카드를 `memo`로 감싼다.
- **드래그 중 검사(측정 보고 결정):** 지금은 드래그로 위치가 바뀔 때마다 그래프 전체를 다시 검사한다(`validateGraph`). 검사 결과는 위치와 상관없으므로, 벤치의 렌더 시간과 브라우저 성능 기록에서 검사가 눈에 띄게 크면 위치만 바뀐 경우 이전 결과를 다시 쓴다. 크지 않으면 하지 않는다.
- **기대 결과:** 선택 변경 10회의 노드 리렌더가 "노드 수 × 10"에서 "바뀐 노드 수(보통 2) × 10"으로 줄어든다. 드래그는 끄는 노드만 다시 그린다.

### 9-b. 번들과 LCP·INP
- **LCP**(Largest Contentful Paint): 페이지를 열었을 때 화면에서 가장 큰 내용(제목, 목록, 캔버스 등)이 그려지기까지 걸린 시간. 화면이 "떴다"고 느끼는 시점이다.
- **INP**(Interaction to Next Paint): 클릭·키 입력 뒤 화면이 바뀌어 보이기까지 걸린 시간. 페이지에서 일어난 조작 중 가장 느린 축에 속하는 값을 쓴다. 눌렀을 때 "굼뜨다"고 느끼는지를 나타낸다.
- 라우트별 JS 크기를 잰다(`next build` 결과). 에디터 번들에 JSONata와 cron-parser(luxon 포함)가 들어간다고 적어 둔 것(M5 정한 것 ①)을 확인한다.
- 목록·에디터·실행 상세의 LCP와, 에디터에서 노드 선택·입력의 INP를 Playwright로 잰다. 측정은 `web-vitals` 라이브러리를 `apps/web`에 더하고, 벤치 빌드(`NEXT_PUBLIC_BENCH=1`)에서만 불러 일반 번들에는 들어가지 않게 한다.
- 측정을 보고 고칠 곳을 정한다. 후보: 에디터에서만 쓰는 무거운 모듈을 그 화면에서만 불러오기.

### 9-c. 큰 JSON 보기 (M5 5-e)
- 실행 상세에서 1MB 출력을 열 때의 렌더 시간과 DOM 수를 재는 벤치 시나리오를 더한다(지금 연습용 응답의 `/mock/bytes`는 글자만 돌려주므로, 큰 JSON을 돌려주는 연습용 주소를 하나 더한다).
- 측정을 보고 고친다. 후보: 펼친 줄만 그리기, 긴 목록 가상화.
- 마지막으로 README "구조" 아래에 성능 요약 표(노드 1000개 드래그·선택 변경, 주요 라우트 번들, 1MB JSON 보기)를 넣는다.

## 완료 기준

- 선택 변경 시 노드 리렌더가 바뀐 노드 수만큼으로 줄었다(벤치 표)
- 노드 1000개 드래그의 프레임 p95가 M6 기준선보다 줄었다
- 번들·LCP·INP와 1MB JSON 보기의 측정값, 개선 결과(또는 고치지 않은 이유)가 `PERFORMANCE.md`에 있다
- README에 성능 표가 있다
- lint·타입 체크·테스트·빌드·e2e 통과

## 정한 것 (2026-10-16)

- M5의 5-e(큰 JSON 보기)를 M9에 넣는다(9-c).
- LCP·INP는 `web-vitals` 라이브러리로 잰다. Chrome과 같은 계산 방식이라 숫자를 믿을 수 있다.
- 숫자 목표는 미리 정하지 않는다. 완료 기준은 "바뀐 노드만 다시 그린다", "M6 기준선보다 줄었다"로 둔다.

## 결과 (2026-10-16)

자세한 표는 `docs/PERFORMANCE.md`의 "M9 9-a", "9-b", "9-c".

| 단계 | 결과 |
|---|---|
| 9-a 에디터 리렌더 | 노드 1000개 드래그 프레임 p95 66.6 → 16.8ms, 렌더 시간 합 1,562 → 73ms. 선택 변경 10회에 다시 그린 노드 10,000 → 20. 드래그 중 검사 다시 쓰기도 넣었다(노드 1000개 검사 한 번이 16.5ms였다). 노드 카드 `memo`는 필요 없었다 |
| 9-b 번들 | 목록 380 → 325KB, 실행 상세 443 → 387KB, 에디터 487KB 그대로. LCP·INP는 로컬에서 모두 수십~200ms대. zod 언어 파일(약 40KB)은 그대로 두었다(BACKLOG) |
| 9-c 큰 JSON | 0.94MB 출력에서 요소 4만 5천 개, 가장 긴 작업 221ms. 드문 경우라 고치지 않았다(BACKLOG) |

계획과 달라진 점:
- `web-vitals`는 `apps/web`에 넣지 않고 Playwright가 페이지를 열 때 주입했다. 앱 번들을 건드리지 않는다.
- 9-b에서 원래 생각한 "cron 검사를 그래프 형식 검사에서 떼기"는 필요 없었다. 형식 검사는 처음부터 설정을 보지 않았고, 노드 종류 목록이 설정 규칙을 끌어오던 것이 원인이었다.
