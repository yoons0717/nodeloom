# M1 core 계획

> 상위 문서: `docs/PROJECT_PLAN.md` 6절 M1. **상태: 승인됨 (2026-10-06).** 노드 id는 `crypto.randomUUID()`, 참조 키 자동 생성은 `<type>_<n>`, HTTP 재시도 기본값은 0회.

`packages/core`에 그래프 모델과 규칙을 순수 TypeScript로 만든다. 에디터(M2)의 즉시 피드백과 서버(M3, M5)의 최종 검증·실행이 이 코드를 같이 쓴다.

## 완료 기준

| 완료 기준 | 확인 방법 |
|---|---|
| 아래 1~5의 규칙마다 성공 케이스와 실패 케이스 단위 테스트가 있고 통과한다 | `pnpm --filter @nodeloom/core test` |

## 작업

### 1. 그래프 모델과 노드 스키마 (zod 4)
- 그래프: `{ schemaVersion, nodes, edges }` (B-8)
- 노드: `{ id, key, type, title, position, config }`
  - `id`: `crypto.randomUUID()`
  - `key`: 참조 키(3-4). 형식 `^[a-z][a-z0-9_]*$`, 그래프 안에서 유일. 자동 생성은 `<type>_<n>`
- 엣지: `{ id, from: { node, port }, to: { node, port } }`
- 노드 종류별 포트와 설정(3-1, 3-3, A-3)

| 종류 | 입력 포트 | 출력 포트 | 설정 |
|---|---|---|---|
| trigger | 없음 | `out` | `cron`(문자열 또는 없음), `testInput`(JSON) |
| http | `in` | `out` | `method`, `url`, `query`, `headers`, `body`(JSONata 식), `timeoutSec`(1~30, 기본 10), `retry`(0~5, 기본 0), `continueOnNon2xx`(기본 false) |
| transform | `in` | `out` | `expression` |
| condition | `in` | `true`, `false` | `expression` |

### 2. 그래프 검증
- 결과는 문제 목록: `{ code, message, nodeId?, edgeId? }`. 에디터 배지(ED-05)와 서버의 실행 전 검증(7-5)이 같이 쓴다
- 규칙:
  - 노드 설정이 스키마에 맞지 않음
  - 참조 키 형식 오류, 중복 참조 키
  - Trigger가 정확히 1개가 아님(A-4)
  - Trigger에서 닿지 않는 노드(A-4)
  - 순환
  - 같은 포트 쌍의 중복 연결, 자기 연결
  - 존재하지 않는 포트, 방향이 틀린 연결(출력 → 입력만 허용)
  - 없는 참조 키를 가리키는 `$nodes.<key>`(3-4)
  - JSONata 문법 오류(A-5의 1차 범위: 문법 검사만)
- 연결 시도 판정: `canConnect(graph, from, to)`가 허용 여부와 거부 사유를 돌려준다. 에디터는 React Flow의 `isValidConnection`에 연결해 쓴다(5-1)

### 3. 위상 정렬
- 실행 순서(7-1)와 순환 검사에 쓴다
- 순환이 있으면 정렬 대신 순환에 걸린 노드를 돌려준다

### 4. 합류와 분기 판정 (7-2)
- 노드 하나의 다음 상태 판정: 부모들의 상태와 Condition 포트 선택을 받아 `run` / `skip` / `wait` 중 하나를 돌려준다
  - 선택되지 않은 Condition 포트에서 온 연결은 SKIPPED로 취급
  - 부모가 하나: 부모가 성공이면 `run`, SKIPPED·FAILED면 `skip`
  - 부모가 여럿: 하나라도 끝나지 않았으면 `wait`, 모두 끝났고 성공이 하나 이상이면 `run`, 아니면 `skip`
- 입력(루트) 만들기: 부모가 하나면 그 출력, 여럿이면 성공한 부모만 `{ 참조키: 출력 }`

### 5. 템플릿과 참조 추출
- 문자열 칸의 `{{ 식 }}` 구간을 나눈다(URL, 헤더, 쿼리)
- 식에서 `$nodes.<key>` 참조를 뽑아 2번 검증에 넘긴다
- JSONata 2.2를 core 의존성으로 추가한다(문법 검사용. 실행은 M5)

## M1에서 하지 않는 것
- cron 식 검증과 다음 실행 시각 계산 → M6(스케줄)
- JSONata 식 실행, 가드레일 → M5
- 커맨드 스택(Undo) → M2(web)
- 실행 상태 저장, 재시도 판정 → M5

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 검증 규칙이 늘면서 문제 목록 형식이 흔들림 | 1번에서 `code` 목록을 먼저 정하고, 테스트가 `code`로 판정 |
| 합류 판정이 M5 실행 엔진의 요구와 어긋남 | 상태를 받아 판정만 돌려주는 순수 함수로 두고, 실행 엔진은 이 함수를 반복 호출만 한다 |
| JSONata가 web 번들을 키움 | M2·M4의 번들 측정(5-3 ②)에서 확인. 필요하면 에디터 경로로만 지연 로딩 |
