# M8 문서 정리와 README

> **상태: 완료 (2026-10-16).** 상위 문서: `docs/PROJECT_PLAN.md` 4절.

## 왜 하나

처음 보는 사람이 README만 보고 무엇인지, 어떻게 짜였는지, 어떻게 실행하는지 알 수 있어야 한다. 그런데 지금 문서는 많고 서로 겹친다.

- **README와 PROJECT_PLAN이 겹친다.** 한 줄 소개, 기술 스택(4절), 구조(5절), 한계(7절 "주의할 점")가 README에 들어갈 내용과 같다.
- **끝난 일의 진행 기록이 남아 있다.** 마일스톤 문서 M0~M7에 "작은 결정 (승인 시 함께 확정)", "완료 보고 형식", "진행 상황" 같은 진행용 절이 있다. PROJECT_PLAN 8절 확인 목록은 대부분 M0~M4에서 끝났다.
- **같은 규칙이 두 곳에 있다.** `RESPONSIVE.md`의 원칙·공통 규칙은 `DESIGN.md` "반응형"에 이미 옮겨져 있다. 남은 것은 문제 분석과 작업 순서(끝남), 구현하면서 달라진 점이다.
- **읽을 수 없는 문서를 가리킨다.** `DECISIONS.md`는 저장소에 없는데, README 링크와 문서 속 결정 번호(`7-2`, `K-3`, `주제 2-1`, `리뷰 C-1` 등, 문서 9개에 100곳 넘게)가 그것을 가리킨다.

## 하지 않는 것

- 코드 수정. 화면 이미지를 찍는 Playwright 스크립트 하나만 더한다. 코드 주석의 `DECISIONS 7-2` 같은 번호(파일 65개, 134곳)는 그대로 두고, 공개 배포 전에 정리하도록 BACKLOG에 적는다.
- 성능 개선. 다음 마일스톤(M9)으로 따로 뺀다. README에는 지금 기준선(`PERFORMANCE.md`)만 링크한다.
- `DESIGN.md`·`CONVENTIONS.md`·`PERFORMANCE.md`의 내용 바꾸기. 겹침과 읽을 수 없는 참조만 정리한다. CONVENTIONS의 "코드 주석에 결정 번호를 남긴다" 규칙은 BACKLOG 항목을 처리할 때 함께 바꾼다.

5. **한계:** PROJECT_PLAN 7절에서 사용자에게 의미 있는 것만 옮긴다
6. **문서:** 저장소에 있는 문서만 링크(지금 빠진 `PERFORMANCE.md` 포함, 없는 `DECISIONS.md` 링크는 뺌)
