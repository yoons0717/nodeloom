# M7 core 테스트 보완

> **상태: 완료 (2026-10-15).** 상위 문서: `docs/PROJECT_PLAN.md` 4절.

## 왜 하나

`packages/core`의 기존 테스트는 대표적인 경우만 한 번씩 확인한다. 그래서 코드가 틀려도 테스트가 통과하는 곳이 있다.

- **경계값을 한쪽만 확인한다:** `timeoutSec`는 31이 거부되는지만 본다. 상한을 30에서 29로 잘못 바꿔도 테스트는 통과한다.
- **걸러져야 할 값을 처음부터 넣지 않는다:** 건너뛴 부모의 출력이 입력에서 빠지는지 확인하는데, 그 출력을 처음부터 넘기지 않는다. 걸러 내는 코드를 지워도 테스트는 통과한다.

이런 곳은 뮤테이션 테스트로 찾는다. 처음 점수는 81.15%다(`2585875` 기준).

## 뮤테이션 테스트의 동작

Stryker가 원본 코드를 한 군데만 바꾼 버전(뮤턴트, 예: `.max(30)` 지우기, `>`를 `>=`로)을 만들고, 뮤턴트마다 기존 테스트를 돌린다. 테스트가 실패하면 잡은 것이고, 통과하면 살아남은 것이다. 살아남은 뮤턴트가 테스트의 빈틈이고, 기존 테스트 파일에 경우를 더해 메운다. core에서는 바꿀 수 있는 곳이 663군데라 1분 넘게 걸려서, `pnpm test`와 따로 `pnpm --filter @nodeloom/core mutation`으로 필요할 때 돌린다.

api·web, CI, 점수 목표는 범위가 아니었다. 원본 코드는 고치지 않는다.

## 보완한 내용

core 테스트 파일 7개(`graph`, `validate`, `template`, `flow`, `topo`, `evaluate`, `cron`)에서 경계값 양쪽, 걸러져야 할 값을 일부러 넣기, 출발·도착 한쪽만 틀린 경우, id와 참조 키가 다른 예시 데이터를 더했다. 기대값은 코드를 실행한 결과가 아니라 규칙(코드 주석, 문서)을 보고 정했다. 이렇게 찾은 확인 방법은 `docs/CONVENTIONS.md` 5장에 규칙으로 적었다.

### 리포트 읽는 법

`pnpm --filter @nodeloom/core mutation`을 실행하면 터미널에 살아남은 뮤턴트 목록과 파일별 표가 나오고, `packages/core/reports/mutation/mutation.html`에 같은 내용이 소스 코드와 함께 저장된다.

- 파일별 점수 색은 점수 구간이다(Stryker 기본값: 80% 이상 초록, 60~80% 노랑, 60% 미만 빨강). `graph.ts`(61%)와 `evaluate.ts`(70%)가 노란색인 것은 남은 뮤턴트가 거의 오류 문구이기 때문이다. 문구를 테스트로 고정하면 초록이 되지만, 판정은 `code`로 한다는 규칙(CONVENTIONS 5장)에 따라 넘긴다.
- 소스 코드 화면의 표시: Killed(잡음), Survived(살아남음), NoCoverage(지나는 테스트가 없음), Timeout(시간 초과). Timeout은 바꾼 코드가 끝나지 않는 반복문이 된 경우로(예: `i++`를 `i--`로), 잡은 것으로 센다.
