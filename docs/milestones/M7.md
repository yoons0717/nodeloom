# M7 core 테스트 보완

> 상위 문서: `docs/PROJECT_PLAN.md` 6절 M7. **상태: 완료 (2026-10-15).**

## 왜 하나

`packages/core`의 기존 테스트는 대표적인 경우만 한 번씩 확인한다. 그래서 코드가 틀려도 테스트가 통과하는 곳이 있다.

- **경계값을 한쪽만 확인한다:** `timeoutSec`는 31이 거부되는지만 본다. 상한을 30에서 29로 잘못 바꿔도 테스트는 통과한다.
- **걸러져야 할 값을 처음부터 넣지 않는다:** 건너뛴 부모의 출력이 입력에서 빠지는지 확인하는데, 그 출력을 처음부터 넘기지 않는다. 걸러 내는 코드를 지워도 테스트는 통과한다.

이런 곳은 뮤테이션 테스트로 찾는다. 처음 점수는 81.15%다(`2585875` 기준).

## 뮤테이션 테스트의 동작

뮤테이션 테스트는 테스트를 새로 쓰는 방식이 아니라, **기존 테스트가 버그를 잡아내는지 점검하는 도구**다.

1. Stryker가 원본 코드를 한 군데만 바꾼 버전(뮤턴트)을 만든다. 예: `.max(30)` 지우기, `>`를 `>=`로, 조건을 `true`로.
2. 뮤턴트마다 기존 테스트를 그대로 돌린다. 테스트가 실패하면 그 뮤턴트를 "잡은" 것이고, 통과하면 "살아남은" 것이다.
3. 살아남은 뮤턴트가 테스트의 빈틈이다. 빈틈은 기존 테스트 파일(`*.test.ts`)에 경우를 더해 메운다.

core에서는 바꿀 수 있는 곳이 663군데라 테스트를 663번 돌린다.

| | `pnpm test` | `pnpm --filter @nodeloom/core mutation` |
|---|---|---|
| 확인하는 것 | 코드가 규칙대로 동작하는가 | 테스트가 코드의 잘못을 잡아내는가 |
| 테스트 실행 | 원본 코드에 한 번 | 뮤턴트마다 한 번 |
| 걸리는 시간 | 몇 초 | 1분 넘게 |
| 언제 | 코드를 고칠 때마다, 커밋 전 | core 테스트를 고친 뒤 필요할 때 |

기존 테스트와 `pnpm test`는 바뀌지 않는다. 새로 생기는 것은 Stryker 설정 파일(`packages/core/stryker.config.json`)과 `mutation` 명령뿐이다.

api·web, CI, 점수 목표는 이번 범위가 아니다. 원본 코드는 고치지 않는다. 실제 버그를 발견하면 고치기 전에 먼저 묻는다.

## 보완한 내용

**현재**는 보완 전 테스트를 가리킨다. 기대값은 규칙(주석, DECISIONS, 문서)을 보고 정한다. 코드를 실행해서 나온 값을 그대로 옮겨 적지 않는다.

### `graph.test.ts`
- **현재:** HTTP `timeoutSec`는 31이 거부되는지만 확인한다.
- **보완:** 경계 양쪽을 모두 확인한다. `timeoutSec`는 0·31·1.5 거부, 1·30 통과. `retry`는 -1·6·1.5 거부, 0·5 통과.
- **현재:** 그래프 형식은 노드 종류만 확인한다.
- **보완:** 노드 위치가 숫자가 아니면 거부되는지 확인한다.

### `validate.test.ts`
- **현재:** 잘못된 참조 키는 대문자(`Cond`)만 확인한다.
- **보완:** 끝에 허용되지 않는 글자가 붙은 키(`http_1-x`)도 거부되는지 확인한다.
- **현재:** 없는 노드와 틀린 포트를 연결 하나로 한 번씩만 확인한다. `canConnect`에는 없는 노드 테스트가 없다.
- **보완:** `validateGraph`와 `canConnect` 모두 출발 쪽만 틀린 경우와 도착 쪽만 틀린 경우를 나눠서 확인한다.
- **현재:** 중복 연결은 출발·도착·포트가 모두 같은 경우만 확인한다.
- **보완:** 출발 포트, 도착 노드, 도착 포트 중 하나라도 다르면 중복이 아니다. 예: Condition의 참·거짓이 같은 노드로 가는 경우.
- **현재:** 설정 오류가 칸마다 보고되는지만 확인한다.
- **보완:** 한 칸에 오류가 여러 개 있어도 한 번만 보고되는지 확인한다. 예: 쿼리 값 두 개가 모두 문자열이 아닌 경우.
- **현재:** Trigger에서 이어지는지는 갈래가 하나인 흐름으로만 확인한다.
- **보완:** Condition의 참·거짓 갈래가 모두 이어진 것으로 보는지 확인한다.

### `template.test.ts`
- **현재:** 큰따옴표 안의 `}}`와 식 안의 중괄호만 확인한다.
- **보완:** 작은따옴표 안의 `}}`, 문자열 중간의 `}}`(`"ab}}"`), 이스케이프된 따옴표(`"a\"}}"`), 짝이 없는 `}`(`{{ a } b }}`)도 식의 끝으로 보지 않는지 확인한다.
- **현재:** `nodeExpressions`는 URL과 본문의 식만 확인한다.
- **보완:** 쿼리와 헤더의 식도 모으는지 확인한다.

### `flow.test.ts`
- **현재:** if/else 뒤 입력을 확인할 때 건너뛴 부모의 출력을 처음부터 넘기지 않는다.
- **보완:** 건너뛰거나 실패한 부모의 출력을 일부러 넘기고, 입력에서 빠지는지 확인한다.
- **현재:** 예시 노드의 id와 참조 키가 같다. 참조 키 대신 id로 묶어도 통과한다.
- **보완:** id와 참조 키가 다른 노드로 참조 키로 묶이는지 확인한다.

### `topo.test.ts`
- **현재:** 순환 뒤에 노드가 하나 붙은 경우만 확인한다.
- **보완:** 노드가 두 개 이상 이어 붙어 있어도 모두 빠지고 순환만 보고되는지 확인한다. 보완 전에는 한 번만 걸러 내는 코드도 통과했다.

### `evaluate.test.ts`
- **현재:** 없는 값은 빈 문자열, 객체는 JSON으로 바뀌는지 확인한다.
- **보완:** 값이 `null`일 때도 `"null"`이 아니라 빈 문자열이 되는지 확인한다.

### `cron.test.ts`
- **현재:** 다음 실행 시각 계산만 확인한다.
- **보완:** 칸 사이에 공백이 여러 개 있거나 앞뒤에 공백이 있어도 올바른 식으로 인식하는지, 5자리여도 값이 범위를 벗어나면 거부하는지 확인한다.

### 리포트 읽는 법

`pnpm --filter @nodeloom/core mutation`을 실행하면 터미널에 살아남은 뮤턴트 목록과 파일별 표가 나오고, `packages/core/reports/mutation/mutation.html`에 같은 내용이 소스 코드와 함께 저장된다.

- 파일별 점수 색은 점수 구간이다(Stryker 기본값: 80% 이상 초록, 60~80% 노랑, 60% 미만 빨강). `graph.ts`(61%)와 `evaluate.ts`(70%)가 노란색인 것은 남은 뮤턴트가 거의 오류 문구이기 때문이다. 문구를 테스트로 고정하면 초록이 되지만, 판정은 `code`로 한다는 규칙(CONVENTIONS 5장)에 따라 넘긴다.
- 소스 코드 화면의 표시: Killed(잡음), Survived(살아남음), NoCoverage(지나는 테스트가 없음), Timeout(시간 초과). Timeout은 바꾼 코드가 끝나지 않는 반복문이 된 경우로(예: `i++`를 `i--`로), 잡은 것으로 센다.
