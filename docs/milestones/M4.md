# M4 실행 엔진 계획

> 상위 문서: `docs/PROJECT_PLAN.md` 6절 M4. **상태: 계획 (승인 전).**

## 무엇을 만드나

에디터에서 **실행 버튼을 누르면 서버가 흐름을 실제로 실행**하게 만든다. 노드 4종이 실제로 동작하고(HTTP 요청, 식 계산, 참·거짓 갈래), 노드마다 받은 값과 내보낸 값을 기록한다. 실행이 실패하면 지정한 "실패 알림" 흐름을 실행한다. 외부 요청 보안(SSRF)과 비밀값 가리기를 함께 넣는다.

| 항목 | 내용 |
|---|---|
| 위치 | `apps/api/src/executor/`(실행 엔진), `apps/api/src/runs/`(실행 API), `apps/api/src/mock/`(연습용 응답), `packages/core`(식 계산), `apps/web`(실행 버튼, 실행 상태, 실패 알림 설정) |
| 새로 쓰는 것 | pg-boss(작업 대기열), JSONata 실행과 가드레일, Node 내장 `fetch`(undici) + 연결 직전 IP 검사, pino(로그) |
| 쓰지 않는 것 | 정해진 시각 실행(cron), 실행 기록 목록·상세 화면, 30일 정리(M5) |

## 시작 전 확인 (2026-10-07)

| 확인할 것 | 결과 |
|---|---|
| pg-boss를 Prisma 트랜잭션 안에서 쓸 수 있는지 | 됨. pg-boss 12.37의 `send()`에 `db` 옵션이 있고, Prisma 트랜잭션 어댑터(`fromPrisma(tx)`)가 패키지에 들어 있다. 실행 기록 생성과 job 등록을 한 트랜잭션으로 묶는다(6-3). 4-a에서 실제로 돌려 확인한다 |
| JSONata 가드레일이 동작하는 버전 | 됨. 설치된 2.2.2에서 `timeout`, `stack` 옵션이 무한 재귀와 오래 걸리는 식을 끊는 것을 직접 확인(오류 코드 D1012). 배열 길이 제한 `sequence` 옵션도 있다 |
| pg-boss의 ESM 호환 | 됨. ESM 전용 패키지, Node 22.12 이상, Postgres 13 이상. 정해진 시각 실행의 시간대(`tz`)도 지원(M5에서 사용) |

## 직접 확인용 예시: 디스코드 메시지 보내기

실제로 매일 돌릴 흐름(1-2)은 M7 전까지 미뤘다. M4에서 눈으로 확인할 예시는 **디스코드 채널로 메시지 보내기**로 한다.

```
Trigger(테스트 입력) → HTTP 요청: POST {{ $secrets.DISCORD_WEBHOOK }}, 본문 { "content": "…" }
```

- 디스코드 채널 설정의 웹훅 주소를 `.env`의 `NODELOOM_SECRET_DISCORD_WEBHOOK`에 넣는다. 웹훅 주소는 아는 사람 누구나 그 채널에 글을 쓸 수 있는 비밀값이다
- HTTP 요청, 본문 식 계산, 비밀값 사용과 가리기(실행 기록에 `***`)를 한 번에 확인할 수 있다
- 자동 테스트와 CI는 디스코드 대신 연습용 응답(`/mock/*`)으로 돌린다

## 완료 기준

| 완료 기준 | 확인 방법 |
|---|---|
| 에디터에서 실행 버튼을 누르면 흐름이 끝까지 실행되고, 실행 상태(진행 중 / 성공 / 실패)가 보인다. 예시 흐름으로 실제 디스코드 채널에 메시지가 온다 | 브라우저와 디스코드에서 확인 |
| 실행 엔진 규칙이 실제 Postgres 통합 테스트로 확인된다: Condition이 고르지 않은 갈래는 건너뜀, 합류, Condition 결과가 참·거짓이 아니면 실패, 재시도하는 실패와 하지 않는 실패, 실행 전체 시간 제한, 서버가 죽었다 이어서 실행할 때 성공한 노드는 다시 실행하지 않음, 같은 흐름 동시 실행 거부, 실패 알림 실행(연쇄 없음), 사설 IP 차단, 비밀값 가리기, 실행 중 삭제 거부 | `pnpm --filter @nodeloom/api test` |
| 전체 lint, 타입 체크, 테스트, 빌드, e2e와 CI가 통과한다 | `pnpm turbo run lint typecheck test build`, `pnpm e2e`, GitHub Actions |

## 데이터

```prisma
model Run {
  id            String    @id @default(uuid()) @db.Uuid
  workflowId    String    @db.Uuid            // 워크플로우를 지우면 실행 기록도 함께 지운다(B-4)
  status        RunStatus                    // PENDING · RUNNING · SUCCESS · FAILED
  kind          RunKind                      // MANUAL · SCHEDULE · FAILURE (A-1)
  graph         Json                         // 실행할 때의 그래프 스냅샷. 실행과 재개는 이것만 읽는다(2-4, B-9)
  triggerInput  Json                         // Trigger가 내보낼 값(B-10)
  error         Json?
  createdAt, startedAt, finishedAt
}

model NodeRun {
  id, runId, nodeId, nodeKey, attempt        // (runId, nodeKey, attempt) 유니크(7-1)
  status        NodeRunStatus                // RUNNING · SUCCESS · FAILED · SKIPPED
  port          String?                      // Condition이 나간 포트
  input, output, error  Json?                // 저장 직전에 비밀값을 ***로(8-2, D-2)
  startedAt, finishedAt
}
```

- `Workflow`에 `failureWorkflowId`(실패하면 실행할 워크플로우)를 추가한다. 그 워크플로우가 지워지면 비운다(B-4).
- **동시 실행 제한(7-5, A-1):** `runs`에 "같은 워크플로우에서 PENDING·RUNNING은 하나만, 단 실패 알림 실행은 제외"인 부분 유니크 인덱스를 건다. Prisma 스키마로는 표현할 수 없어서 마이그레이션 SQL에 직접 쓴다.

## 실행 흐름

```
실행 버튼 → POST /workflows/:id/runs
  1. 그래프 검사(validateGraph). 문제가 있으면 422와 문제 목록(7-5)
  2. 한 트랜잭션: Run 생성(그래프 스냅샷) + pg-boss job 등록. 이미 실행 중이면 409(7-5)
  3. 202 { runId }. 화면은 1초마다 상태만 조회(B-1)

워커(같은 프로세스, 7-6) → job 하나 = 실행 하나(7-1)
  4. 스냅샷을 읽고, 이미 성공한 노드는 저장된 결과를 다시 씀(재개)
  5. 반복: 대기 중인 노드마다 decideNode → 실행 / 건너뜀 / 기다림. 실행할 노드들은 동시에(Promise.all)
  6. 노드가 끝날 때마다 node_runs에 저장(비밀값 가림)
  7. 모두 끝나면 Run을 SUCCESS 또는 FAILED로. 실행 전체가 5분을 넘으면 FAILED(RUN_TIMEOUT)
  8. FAILED이고 실패 알림 워크플로우가 지정돼 있으면 그 흐름을 실행. 실패 알림 흐름이 검사에 걸리거나 실행 중 실패해도 FAILED로 기록만 하고 다시 알림을 보내지 않는다(7-4, 7-5)
```

## 노드 실행기

| 노드 | 하는 일 |
|---|---|
| Trigger | 실행 종류에 맞는 입력을 그대로 내보낸다(수동: 테스트 입력, 실패 알림: `{ workflow, runId, failedNode, error }`, B-10) |
| Transform | 식을 계산한 결과를 내보낸다 |
| Condition | 식을 계산해 정확히 `true`면 참 포트, `false`면 거짓 포트. 그 밖의 값이면 실패(A-2) |
| HTTP 요청 | URL·쿼리·헤더의 `{{ }}`를 채우고 본문 식을 계산해 요청. 2xx가 아니면 실패. "다음 노드로 진행"이 켜져 있으면 응답 코드와 관계없이 `{ status, body }`, 꺼져 있으면 본문만 내보냄(3-3). 응답은 1MB까지 |

- **식 계산(3-2):** 앞 노드 결과가 루트, `$nodes.<참조 키>`, `$run`(`{ id, workflowId, kind, startedAt }`), `$secrets`를 넘긴다. `{{ }}` 안의 값이 없으면 빈 글자로 채운다. 가드레일: 1초, 재귀 깊이, 배열 길이(7-3).
- **재시도(7-3):** 연결 실패, 타임아웃, 5xx, 408, 429만. 1·2·4초…(최대 30초) + 흔들림(jitter). job 안에서 반복하고 시도 번호를 기록한다.
- **보안(8-1, B-7):** http·https만. 연결 직전에 실제 IP를 검사해 loopback·사설·링크 로컬은 막는다(`HTTP_ALLOW_PRIVATE`에 적은 대상만 허용). 클라우드 메타데이터 주소는 항상 막는다. 리다이렉트는 따라가지 않는다. `MOCK_BASE_URL`만 예외. 데모 모드에서는 `MOCK_BASE_URL`만 허용(1-3).
- **비밀값(2-3, 8-2):** `NODELOOM_SECRET_*` 환경 변수만 `$secrets`로 쓴다. 8자 미만이면 서버가 시작하지 않는다. 입력·출력·오류를 저장하기 직전과 로그를 남기기 직전에 비밀값(원래 값과 URL 인코딩 값)을 `***`로 바꾼다.

## 단계

다섯 단계로 나누고 단계마다 보고하고 멈춘다.

### 4-a. 실행 기록 테이블과 대기열
- **파일:** `prisma/schema.prisma`, 마이그레이션(부분 유니크 인덱스 직접 작성), `src/executor/queue.ts`(pg-boss 시작·종료)
- **내용:** `runs`, `node_runs`, `failureWorkflowId`. pg-boss를 앱과 같은 DB의 별도 스키마(`pgboss`)로 시작
- **테스트:** 같은 워크플로우에 실행 중인 기록이 둘이 될 수 없다(실패 알림 실행은 예외). 실행 기록 생성과 job 등록이 한 트랜잭션이라 하나가 실패하면 둘 다 남지 않는다

### 4-b. 식 계산과 노드 실행기
- **파일:** `packages/core/src/evaluate.ts`(식 계산, `{{ }}` 채우기), `src/executor/nodes/*.ts`, `src/mock/`(연습용 응답)
- **내용:** 노드 4종 실행기, HTTP 재시도·시간 제한·응답 크기 제한. 연습용 응답: 날씨 예시, 받은 요청 기록, 지정한 상태 코드, 느린 응답(시간 제한 시험용)
- **테스트:** core 단위 테스트(식 계산, 가드레일, `{{ }}` 채우기), 실행기 테스트(연습용 응답 서버 대상: 재시도하는 실패와 하지 않는 실패, 2xx 기준, 응답 크기, Condition 결과가 불리언이 아님)

### 4-c. 실행 엔진
- **파일:** `src/executor/run-executor.ts`, `src/executor/executor.module.ts`
- **내용:** job 하나로 흐름 하나 실행, 병렬 갈래, 재개, 실행 전체 시간 제한, 실행 상태 확정, 실패 알림 실행
- **테스트(Testcontainers):** 갈래 건너뜀, 합류(성공·실패·건너뜀이 섞인 경우), 전체 시간 제한, 재개 시 성공한 노드를 다시 실행하지 않음, 실패 알림 실행과 연쇄 없음

### 4-d. 외부 요청 보안과 비밀값 가리기
- **파일:** `src/executor/http/ssrf.ts`, `src/executor/mask.ts`, `src/env.ts`(비밀값 검사), pino 로거
- **내용:** 연결 직전 IP 검사(DNS를 바꿔치기해도 연결하는 IP를 검사), 메타데이터 주소 차단, 허용 목록, 데모 모드 제한. 저장·로그 직전 비밀값 가리기. 로그에 `runId`를 붙인다
- **테스트:** 사설·loopback·메타데이터 주소 차단, 허용 목록, 리다이렉트를 따라가지 않음, 입력·출력·오류·로그에 비밀값이 남지 않음(원래 값과 URL 인코딩 값)

### 4-e. 실행 API와 화면
- **파일:** `src/runs/`(실행 시작, 상태 조회), `src/workflows/`(삭제 규칙, 실패 알림 설정), `apps/web/src/features/runs/`, 에디터 상단 바, HTTP 설정 화면
- **내용:**
  - `POST /workflows/:id/runs`(검사 실패 422, 실행 중 409, 시작 202), `GET /runs/:id/status`(상태와 노드별 상태만, B-1)
  - 실행 중이면 삭제 거부, 삭제하면 실행 기록도 함께, 다른 워크플로우의 실패 알림 설정은 비움(B-4)
  - 에디터: 실행 버튼, 저장되지 않은 변경이 있으면 먼저 저장, 상단 바에 실행 상태(1초 조회), 검사 실패 사유 표시
  - 워크플로우의 "실패하면 실행할 워크플로우" 선택(7-4)
  - HTTP 설정에 "최악의 경우 걸리는 시간" 표시(제한 시간 × 시도 횟수 + 대기 시간, B-13)
- **테스트:** 동시 실행 거부(409), 검사 실패(422), 실행 중 삭제 거부, 삭제 시 실패 알림 설정 비움. 실행 버튼 RTL 1개

| ⑦ | 실행 전 저장 | 실행 버튼은 저장되지 않은 변경이 있으면 먼저 저장하고 실행(서버는 저장된 그래프로 실행) | 저장되지 않았으면 실행 버튼을 막음 |

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 실행 중 서버가 죽으면 같은 HTTP 요청을 다시 보낼 수 있음 | "최소 한 번 실행" 한계로 둔다(B-2). 성공을 기록한 노드는 다시 실행하지 않는다. README에 적는다(M6) |
| DNS를 바꿔치기해서 검사를 통과한 뒤 사설 IP로 연결(DNS 재바인딩) | 이름을 IP로 바꾼 뒤 그 IP로 직접 연결한다. 검사와 연결 사이에 다시 이름을 풀지 않는다 |
| 식이 무한히 돌거나 큰 배열을 만들어 서버가 멈춤 | JSONata 가드레일(시간 1초, 재귀 깊이, 배열 길이) + 실행 전체 5분 |
| 병렬 갈래가 동시에 같은 기록을 고침 | 노드마다 자기 줄만 쓴다. `(runId, nodeKey, attempt)` 유니크 제약 |
| 실행 엔진 테스트가 느리고 불안정함(시간, 재시도 대기) | 대기 시간과 시간 제한을 테스트에서 줄일 수 있게 설정으로 받는다. 시간을 다루는 판단은 순수 함수로 떼어 단위 테스트 |
| 데모 서버에서 외부로 요청이 나감 | 데모 모드에서는 `MOCK_BASE_URL`만 허용. 통합 테스트로 확인 |

## 완료 보고 형식

단계(4-a~4-e)마다 만든 파일과 역할, 확인할 것을 보고하고 멈춘다. 핵심 작업(대기열, 실행 엔진, SSRF)은 시작 전에 개념을 짧게 설명하고 예측 질문을 한다. 마지막에 완료 기준 확인 결과를 보고한다. 커밋은 매번 먼저 묻는다.
