# Nodeloom 프로젝트 계획

> 이 문서는 "무엇을 만들고 어떤 순서로 하는가"를 정리한다. 기술 스택, 구조, 한계는 `README.md`, 미룬 아이디어는 `docs/BACKLOG.md`, 마일스톤마다 한 일은 `docs/milestones/`에 있다.

## 1. 목표

**노드 기반 워크플로우 자동화 도구**(Node-based workflow automation). 노드를 이어 붙여 반복 작업 흐름을 만들고, 서버가 대신 실행해 준다. 1인용.

- **1순위: 기술적 완성도.** 인터랙티브 에디터, 측정 가능한 렌더링 최적화, 모노레포, 가벼운 NestJS 백엔드와 실행 엔진.
- **2순위: 실제 사용.** MVP 완료 시점에 실사용 흐름 1개가 매일 스케줄로 돌아간다.
- 공개 데모는 방문자가 에디터를 직접 만져 보는 제한 모드(연습용 응답 `/mock`으로만 실행)다. 실제 외부 호출은 개인 서버에서만 한다.

## 2. MVP 범위

MVP는 두 단계로 나눈다. 각 단계에는 막혔을 때 먼저 공개할 **최소선**과 목표인 **완성선**을 둔다.

### 1차: 에디터 (M0~M3, 완료)
| 구분 | 내용 |
|---|---|
| 최소선 | 에디터(노드 4종 추가·이동·연결·삭제, 연결 검증과 거부 사유, Undo/Redo, 설정 패널과 JSONata 문법 검사), 저장·불러오기, 관리자 로그인, 데모 모드, 성능 기준선(20/200/1000) 측정 |

### 2차: 실행 엔진과 실사용
| 구분 | 내용 |
|---|---|
| 최소선 | 실행 엔진(노드 4종 실행, 분기·합류, 재시도·시간 제한, SSRF 방어, 마스킹), 수동 실행, 실행 기록·상세 화면(폴링), 스케줄, 실패 알림 워크플로우, README(화면 이미지, 아키텍처, 실행 방법), **실사용 흐름을 개인 서버에 스케줄로 등록해 매일 실행 시작** |
| 완성선 | 최소선 + 실사용 흐름 7일 연속 성공(MVP 완료 기준), 성능 개선 전후 수치(① 노드 리렌더와 프레임 시간 ② 라우트별 번들, LCP·INP ③ 큰 JSON 보기)를 README 표로 정리, 마지막 실행 데이터로 표현식 미리보기 |

### MVP 밖 (요약, 전체 목록은 BACKLOG)
다중 사용자와 화면 시크릿 관리, 버전 목록·복원, 코드 노드, 상태 저장 노드, 노드별 오류 포트, SSE, 미니맵, 복사·붙여넣기, 웹훅 트리거, 휴대폰 편집, 데모 자동 초기화.

## 3. 핵심 동작 규칙

| 영역 | 규칙 |
|---|---|
| 노드 | Trigger(정확히 1개, 수동과 cron 스케줄), HTTP, Transform, Condition(참·거짓 포트) |
| 값 참조 | JSONata 2.2 이상. 루트는 직전 노드 출력. 부모가 여럿이면 `{ 참조키: 출력 }`. 다른 노드는 `$nodes.<참조키>`, 비밀값은 `$secrets.NAME`. 문자열 칸은 `{{ }}`, HTTP 본문은 JSONata 식 |
| 실행 | 실행 1개 = job 1개. 위상 정렬 순서로 실행하고 병렬 갈래는 동시에. 재시작하면 성공한 노드는 건너뛰고 이어서 실행. 항상 실행 기록에 복사해 둔 그래프만 읽는다 |
| 분기·합류 | 선택되지 않은 포트 쪽은 SKIPPED. 부모가 여럿이면 하나라도 성공했을 때 실행. Condition 결과가 불리언이 아니면 FAILED |
| 실패 | HTTP는 연결 실패, 타임아웃, 5xx, 408, 429만 지수 백오프로 재시도. 최종 실패하면 하위 노드는 SKIPPED, 실행은 FAILED, 지정한 실패 알림 워크플로우를 실행 |
| 시간 제한 | HTTP 1~30초(기본 10초), JSONata 1초, 실행 전체 5분(`RUN_TIMEOUT`) |
| 동시 실행 | 워크플로우당 1개(부분 유니크 인덱스). 실패 알림 실행은 예외 |
| 검증 | 저장은 자유(초안). 실행은 서버가 core로 다시 검증. 스케줄 실행에서 검증에 실패하면 실행을 FAILED로 남긴다 |
| 보존 | 끝난 실행 기록은 30일 보존(`RUN_RETENTION_DAYS`). 데모에서는 정리 작업도 돌지 않는다 |

## 4. 마일스톤과 완료 기준

기간은 정하지 않는다. 마일스톤마다 "계획 → 승인 → 구현 → 완료 기준 확인 → 멈춤" 순서로 진행하고, 상세 계획과 기록은 `docs/milestones/M<n>.md`에 둔다. **(완성선)** 항목은 막히면 뒤로 미룰 수 있다.

- 1차 = M0~M3
- 2차 최소선 = M4 + M5(완성선 제외) + M8 README + M10 실사용 시작. 2차 완성선 = 나머지(M5의 5-e·5-f, M9 성능 개선, 7일 연속 성공)
- M6 디자인 정리와 M7 테스트 보완은 최소선·완성선과 별개다

| 마일스톤 | 내용 | 상태 |
|---|---|---|
| M0 기반 | 모노레포, web·api 뼈대, Postgres, Prisma, Testcontainers, CI | 완료 |
| M1 core | 그래프 타입, 노드 스키마, 검증, 위상 정렬, 합류 판정, 템플릿 | 완료 |
| M2 에디터 | React Flow 캔버스, 팔레트, 연결 검증, Undo/Redo, 설정 패널, 성능 기준선 | 완료 |
| M3 저장·인증·데모 | 워크플로우 저장, 관리자 로그인, 데모 모드, 첫 e2e | 완료 |
| M4 실행 엔진 | pg-boss 실행, 노드 4종 실행기, 재시도·시간 제한, SSRF 차단, 비밀값 가리기, 실패 알림 | 완료 |
| M5 스케줄·실행 화면 | cron 스케줄, 실행 기록·상세, 30일 정리. (완성선) 큰 JSON 보기, 마지막 실행 데이터 미리보기 | 최소선 완료 |
| M6 디자인 정리 | 색 토큰, 부품, 노드 카드, 사이드바, 도움말, 반응형 | 완료 |
| M7 core 테스트 보완 | 뮤테이션 테스트로 core 테스트의 빈틈을 찾아 메움 | 완료 |
| M8 문서 정리·README | 겹치는 문서 정리, README(화면 이미지, 구조, 한계) | 완료 |
| **M9 성능 개선** | (완성선) ① 노드 리렌더와 프레임 시간 ② 라우트별 번들, LCP·INP. 전후 수치를 `docs/PERFORMANCE.md`와 README에 기록 | |
| **M10 실사용·MVP 마감** | 실사용 흐름 확정, 워크플로우 이름 중복 금지(DB 유니크, 409, 새 워크플로우는 서버가 번호를 붙임), 개인 서버 배포와 공개 데모 배포, 운영 가이드 | |

M10 완료 기준: 실사용 흐름 스케줄 등록과 첫 성공, 의도적 실패로 실패 알림 수신 확인, 같은 이름으로 만들기·저장 거부(최소선). 7일 연속 성공(완성선). **7일 연속 성공 시 MVP 완료 선언.**

## 5. 주의할 점

| 항목 | 내용 |
|---|---|
| SSRF 예외 | `MOCK_BASE_URL`과 `HTTP_ALLOW_PRIVATE`만 예외다. 메타데이터 주소는 어떤 경우에도 차단 |
| bcrypt 해시와 `.env` | 해시의 `$`가 변수로 해석되지 않도록 작은따옴표로 감싼다. `pnpm admin:hash` 출력을 그대로 사용 |
| 시간대 | 서버와 브라우저 모두 `APP_TIMEZONE`으로 시각을 표시(hydration 불일치 방지) |
| 스토어 | Zustand 스토어는 에디터마다 생성. 모듈 전역 스토어 금지 |
| 데모 | 자동 초기화와 기록 정리가 없다. 지저분해지거나 DB가 커지면 시드를 다시 적용 |
| 시간 제한 | HTTP 재시도가 많은 노드가 여럿이면 전체 5분을 넘을 수 있다. 노드 설정에 최악 소요 시간 표시 |
| 방문자 IP | 배포할 때 Next 앞에 리버스 프록시를 두고 실제 IP를 넣게 한다. Next 포트는 밖에 열지 않는다. 없으면 로그인·데모 속도 제한이 동작하지 않거나 우회된다 |
| 범위 | 진행 중 떠오른 아이디어는 BACKLOG에만 추가하고, 현재 마일스톤이 끝나기 전에는 구현하지 않는다 |
